# v0.1 readiness review

Review date: 2026-09-20. Implementation reviewed:
[`d2d0190`](https://github.com/Nazgulion/celandine/commit/d2d01906452109089010180d9ba25084c592dcb7).
This report accompanies manifest/support-documentation changes; it does not tag,
publish, or declare v0.1 complete.

## Result

**The named v0.1 features are implemented and the current checks pass. The
project is not ready to publish under the complete specification yet.**
Unresolved scope differences in the plan and missing performance coverage
remain. The subsequent fuzzing increment closes the dedicated fuzzing setup and
initial-campaign gap described below. `publish = false` stays in place.

The authoritative [project plan](../../finite_sequence_information_complexity_project_plan.md)
contains both a concise release list (§30) and broader foundation/quality
requirements (§§6, 19, 21, 35, 37). Passing the former must not silently waive
the latter. The recommendations below are an audit interpretation, not changes
to the specification or authorization to implement later milestones.

and `license = "MIT"` to the crate manifest. The license choice is resolved.

The review adds the known repository URL and explicit README path to the

### 3. Dedicated fuzzing

The original audit found only fixed-seed properties and exhaustive short binary
n-gram tests. The subsequent [fuzzing increment](../fuzzing.md) adds three
dedicated targets for byte inputs, checked count imports, arbitrary order/base
bit patterns (including nonfinite values), and n-gram lengths. It includes 55
committed seeds, stable replay, separate pinned tooling/lockfile, a reproducible
campaign runner, and bounded CI campaigns with retained failure artifacts.

The [initial campaign](../fuzzing/initial-campaign.md) passed 100,000 ASan
executions per target without a library defect. This closes the missing-target,
corpus, and initial-campaign evidence gap for the existing APIs (§19.18.5 and
§35). It does not establish exhaustive coverage or replace independent numerical
verification; fuzzing continues as functionality changes.

### 4. Complete the specified performance evidence

The entropy harnesses cover 16 B through 10 MiB. The n-gram harness adds some
100 MiB workloads with deliberately bounded support. This does not satisfy a
claim that every entropy API has been measured through the §21/§35 100 MB tier.
Add representative 100 MiB entropy cases while retaining older baselines.

Allocation-call checks and fixed histogram sizes are documented, but peak
memory has not been measured. In particular, n-gram tables allocate storage
proportional to distinct blocks and retain a borrow of the input. Measure their
peak memory on controlled workloads to complete §21.20.2. Cycles per byte are
optional where useful, not a universal missing requirement. This audit did not
repeat unchanged timing measurements.

## Public API and numerical review

No breaking rename is needed for the current byte-oriented release. APIs expose
simple byte entry points and distribution reuse; parameters are validated before
empty-input handling; error types implement `Display` and `Error`. Integer totals
are protected by construction or checked import. The library forbids unsafe code.

Intentional differences are documented and should stay visible:

- Byte probability iteration includes all 256 values; n-gram iteration includes
  observed blocks only, in sorted order. N-gram keys borrow the input, and
  nonempty count construction allocates.
- Rényi accepts positive infinity, Tsallis requires finite orders, and Shannon
  bases must be finite and greater than one. These reflect different formulas.
- Default Shannon, Hartley, Rényi, collision, and min-entropy use bits per symbol.
  Tsallis uses fixed Shannon-bit scaling; explicit Shannon bases select units.
- Empty state returns zero by convention but is not a probability law.
- A distribution is currently an empirical byte law, not a generic arbitrary
  probability vector. That is a scope limitation, not silent normalization.

Numerical behavior is supported by independent fixtures, not universal formal
error bounds. At very large, imbalanced imported counts, Shannon may round a
dominant probability to one and lose its small contribution. Rényi/Tsallis at
exact order one and explicit Shannon bases inherit this documented limitation.
Bases close to one amplify absolute errors. Subnormal high-order Tsallis results
and platform-dependent transcendental functions require runtime testing before
expanding supported platforms. See [numerical behavior](../numerical-behavior.md).

These are accepted limits of the currently documented contract, not evidence
that every accuracy or source-estimation use case is supported. No new
algorithmic defect was established by this audit.

## Validation evidence

On the reviewed implementation, all of the following passed locally with Rust
1.90.0, Linux x86-64, and Python 3.10.12:

```sh
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo test --locked --release
RUSTDOCFLAGS='-D warnings' cargo doc --locked --no-deps
cargo bench --locked --no-run
```

All eight `scripts/reference_*.py --check` commands and all seven
`cargo run --locked --example ...` commands passed. Both test profiles ran the
allocation checks. The [CI run for the same commit](https://github.com/Nazgulion/celandine/actions/runs/35504524236)
also completed successfully on Ubuntu 24.04, Rust 1.90.0, Python 3.12.

`cargo package --locked --offline` passed on the clean reviewed implementation.
After the review's metadata, license, and documentation changes, formatting,
all-target Clippy, and warning-free documentation builds passed again.
`cargo package --locked --offline --allow-dirty` created and verified the updated
105-file package without the earlier missing-metadata warning. Its archive
includes the MIT license, support policy, review, documentation included through
`include_str!`, fixtures, examples, and illustration. `--allow-dirty` permits this
local smoke check before committing; a release must be verified from a clean
commit. Packaging does not run the full test suite; it supplements the checks above.

Four additional targets passed library-only `cargo check`; see
[support policy](../support.md) for target names and the distinction from runtime
validation. There is no Windows/macOS runtime evidence or 32-bit execution claim.
