# LZ76 scalar performance and memory baseline

Measured 2026-10-23 on Linux x86-64, Intel Core i7-13700HX, Rust 1.90.0
(`1159e78c4`, LLVM 20.1.8), Criterion 0.7, using the default optimized bench
profile without custom RUSTFLAGS, affinity, or governor changes. This establishes
a baseline for the allocation-free scalar algorithm; it is not a suffix-index
implementation or an optimization comparison.

## Workloads and units

There are **37 cases**. Constant, cycling, and skewed inputs each run at 16, 64,
256, 1024, 4096, 16384, 65536, 1048576, 10485760, and 104857600 bytes. Mixed inputs
run only through 65536 bytes: the source scan has quadratic worst-case runtime.
Large periodic inputs exercise early termination on a reproducible suffix and
must not be taken as representative of arbitrary data at those sizes.

Shapes match existing benchmarks: constant zeros; cycling `i mod 256`; skewed
one at each index divisible by 100, zero otherwise; mixed xorshift64 with seed
`0x123456789abcdef0`, shifts 13/7/17, and the high byte. Input creation is outside
timing; each measured call returns the exact phrase count. Criterion uses flat
sampling, ten samples, 100 ms warm-up, and a requested 500 ms measurement period
(extended for slow cases). CSV estimates are means with 95% confidence intervals.

Throughput is `input_bytes / 2^20 * 10^9 / latency_ns` MiB/s, counting original
input once, not the many internal byte comparisons. For example, 100 MiB in
0.043 seconds is about 2326 MiB/s. Small latency and large-input throughput
measure different workloads and should not be extrapolated across shapes.

## Results

| Shape | 16 B (ns) | 64 KiB (ms) | 100 MiB (ms) |
| --- | ---: | ---: | ---: |
| Constant | 8.548 | 0.02653 | 42.915 |
| Cycling | 90.530 | 0.04776 | 42.740 |
| Skewed | 12.362 | 0.02656 | 42.633 |
| Mixed | 91.583 | 548.92449 | Not measured |

The 100 MiB counts are 2, 257, and 4 phrases for constant, cycling, and skewed
inputs respectively. Each quickly reaches a suffix reproducible from an earlier
start. The mixed 64 KiB input has 27,902 phrases and repeatedly searches a growing
prefix. This observed cost is a substantial limitation: use the scalar API with
workloads whose size and structure you have assessed. Faster indexing remains a
future implementation improvement, not an undocumented guarantee of this API.

## Memory

The calibrated [memory probe](large-input-memory.md) ran **54 fresh-process
readings**: the three periodic shapes at 10/100 MiB, mixed inputs at 4/16/64 KiB,
input-only controls for each, and three repetitions. Every LZ76 scope reported
**zero peak requested heap bytes and zero allocation calls**. The algorithm keeps
only integer indices and counters; stack high-water usage was not measured.

At 100 MiB, LZ76 process RSS ranged from 104064 to 104448 KiB across these
shapes; input controls had the same combined range. Mixed 64 KiB LZ76 and controls
both ranged from 2112 to 2304 KiB. RSS includes the resident input, runtime,
allocator overhead, and stack and is not an exact auxiliary-memory measurement.
The `support` CSV column stores phrase count for LZ76; `ngram_length` is unused.
Debug/release allocation tests also exercise empty, singleton, published, and
short overlapping inputs, plus cycling buffers through 10 MiB.

## Reproduction and retained evidence

```sh
python3 scripts/benchmark_lz76.py
python3 scripts/measure_memory.py --lz76
cargo test --locked --release --test allocations
```

Timing and memory were run sequentially, without concurrent project tests,
fuzzing, or other benchmarks. The parent commit is `74beb07` (subword complexity);
source SHA-256 hashes identify the measured working-tree LZ76 implementation.

- [Latency CSV](lz76.csv) and [raw Criterion record](lz76-raw.tar.gz): 37 estimates,
  samples, descriptors, outlier data, commands, toolchain/host manifest, and log.
- [Memory CSV](lz76-memory.csv) and [raw memory record](lz76-memory-raw.tar.gz):
  54 readings with commands, hashes, toolchain, and host metadata.

Archived text normalizes the checkout path to `$REPO`. Original outputs remain
under `target/measurements/`. CI compiles the benchmark and checks the memory
smoke case; timings are not shared-runner performance gates. These measurements
are bounded host/workload evidence and do not establish correctness.
